General Chunking Principles
- Object‑level granularity
- Treat each JSON object (epic, story, commit, defect, build, status history) as the atomic unit.
- Never split across objects — semantics are lost if half a story or defect is embedded separately.
- Size limits
- If a single object exceeds the embedding model’s token limit (e.g., very long status histories), apply batch chunking: split the object into logical sub‑sections (e.g., status transitions, comments, commits) but keep a shared primary key (jiraId, epicId, commitId, buildId) so retrieval can reassemble.
- Metadata preservation
- Store both the raw JSON and structured columns.
- Embeddings capture semantic similarity; structured columns enable filtering (e.g., by assignee, environment, status).
- Fallback strategy
- If chunking is required, create multiple embedding rows with the same object key and a chunk_index.
- Example: PROJ-1001_chunk_1, PROJ-1001_chunk_2.
- Retrieval merges chunks by key before presenting to the LLM.

 pgvector column sizing
- pgvector supports dimensions up to 16,384 (the maximum length of a vector).
- Most embedding models (OpenAI, HuggingFace, etc.) produce vectors of size 768, 1024, or 1536.
- To be safe and future‑proof, define your vector columns as vector(1536) unless you know your embedding model dimension.
- If you later switch to a larger model, you can adjust to vector(3072) or higher, but keep below 16,384.
